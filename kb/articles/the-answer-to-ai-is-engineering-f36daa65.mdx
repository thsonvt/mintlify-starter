## Summary

Geoffrey Huntley argues that the solution to AI-related security issues lies in engineering rather than more AI, emphasizing the need for faster incident response and the challenges of open-source dependencies.

## Key Insights

> "the answer to AI is engineering."
>
> — Huntley emphasizes that engineering, not more AI, is the solution to current challenges.

> "you’ll need more inferencing than your attackers."
>
> — He highlights the increasing need for advanced inferencing capabilities to stay secure.

> "patching is perceived to be hard, but it doesn’t have to be."
>
> — Huntley discusses the misconceptions around the complexity of patching software.

## Full Article

The security take-off is here, and the answer isn&apos;t more AI. It&apos;s engineering. I gave a talk at AI DevCon New York about patching the planet with Nix and agents, how I got through the last round of security incidents without losing any sleep, and a bonus round on loops, back pressure and property-based testing.Everyone at the conference spent two days hearing about how to build software faster with factories. Cool. I wanted to talk about something different: how do you respond to security incidents faster? It turns out that if you optimise for incident response times, your build times speed up too. Here&apos;s the talk, written up properly, with the slides broken out and chapter links at the bottom if you want to jump to a specific part.It turns out the answer for AI is engineering.two weeks ago was pretty wild, huh?OpenCode got breached. Then the Prime Minister of Japan was tweeting at everyone to go and update PHP.Next thing you know, there&apos;s a vulnerability in an HTTP stack that lets anyone remotely turn off a running server. Then a 12-year-old GitLab flaw that led to remote code execution on self-managed servers. Ouch.And it turns out the answer to life, the universe, and everything isn&apos;t 42. It&apos;s 4. A certificate authority had a key that should have been a 116-digit number, and it was just 4. Anyone who could guess it could forge HTTPS certificates for any website. The number 4 opens all doors on the internet.So we started wondering: is it time to turn the internet off yet?You&apos;ve probably seen the graph of GitHub pull requests going quadratic, and GitHub having availability issues because of it. That&apos;s agent take-off. Below is the security version of that: the security take-off.I&apos;m putting it to you that this is the start of the new normal. You could argue it&apos;s a bump in the road, and once all the software has been patched, things will calm down. Maybe. But agents are writing software now; agents were trained on existing code, and existing code is full of these vulnerabilities.you&apos;ll need more inferencing than your attackersUnfortunately, cyber is only going to accelerate from here. It&apos;s going to get really weird, because I suspect you&apos;re going to need more inferencing capacity than your attackers to stay secure.Think about the companies right now saying, "oh no, we can only do a &#x24;100-a-month token budget per employee." Yeah, no. As soon as you publish any code on GitHub, someone with racks of inferencing hardware will autonomously scan it and then autonomously make tool calls to exploit what they find. That&apos;s the new state of normal.why do we have open-source dependencies?Almost a year ago I wrote a blog post asking why we even have open-source libraries. I got grilled to hell on Hacker News for it, but every day that goes by it becomes more true.what is the point of libraries now that you can just generate them?It&apos;s a meme as accurate as time. The problem is that our digital infrastructure depends upon just some random guy in Nebraska. Open-source, by design, is not financially sustainable. Finding reliable, well-defined funding sources is exceptionally challenging. As projects grow in size, many maintainers burn out andWe had open-source libraries because code was precious. It was hard to write, so we concentrated it into libraries to make reuse easy. We also did it to make hiring easier: React was famously a play by Facebook to standardise frontend development so they could hire for it. We optimised our practices for humans, and I don&apos;t think we need libraries anymore.I&apos;m not saying you should go and vibe-code your own cryptography. If you&apos;re a cryptographer, please do. I&apos;m not. There&apos;s still going to be a trusted base and a trusted core. But think about your supply chain. How much time do you spend on Dependabot updates? How much time do you spend on incident response because a Dependabot update was compromised, because the upstream author was compromised? We&apos;re already losing time, all because the prior was that writing software was hard.It&apos;s been a year, and I don&apos;t use much open source anymore. Sure, I use the Linux kernel, DNS servers like BIND, and the lower-level stuff. But once I get into higher-level code, I just prompt the agent for what I want. It feels very unnatural at first. If it&apos;s small and well-specified, like a command-line argument parser, you could take that dependency, or you could have Claude build it in a loop. Something magical happens when you do: it&apos;s built for your use case, and you don&apos;t need to get someone on GitHub to merge your pull request. It turns out that if you have to tool call a human, that&apos;s not AGI.So the best you can do is either generate it first-party, or vendor the open-source software and check it into your repo so the agent can modify and extend it. That&apos;s one approach. Today I want to show you a different one.patching is perceived to be hardpatch the planetI don&apos;t know if you&apos;ve seen this, but a CA just got popped. Their keys got leaked, which means the industry as a whole now has some pretty major problems. It was revealed two hours ago. eMudhra Intermediate CA CompromiseeMudhra Intermediate CA Compromise Now you&apos;re probably wonderingI&apos;m calling it patch the planet. Patching is perceived to be hard, but it doesn&apos;t have to be. What makes it hard? Say you want to patch something on GitHub. You have to figure out how that software builds, learn its toolchain, and set up a new CI job just for that one thing. You do that per language, and every open-source library has a different build toolchain. Then once you&apos;ve patched it, you need to host it in an artifact repo, and now you&apos;re thinking about artifact tokens. We make things needlessly complex.the world hasn&#x2019;t figured out yet that you can literally just fix everything with a Nix overlayThere are many things that are uncertain in our industry right now, but one thing I am certain about, and have been for almost 13 years, is that Nix is a terrible programming language. I remember when I first learned it, it felt like pushing shit uphill. The learning cliffThere&apos;s been a solution for a long time: Nix. It&apos;s been around since 2003, and I&apos;ve used it for years. You might have heard that Nix sucks. It does. There&apos;s no silver bullet. The most common complaint is that it&apos;s hard to use. It was. Agents know how to drive towards an outcome, so you just need to know that Nix exists, then prompt the agent: I want Nix here. The same goes for Bazel and Buck2. Talk to any eng leader, and they&apos;ve got a story about nearly getting fired after staffing a team of five to introduce one of these, and then spending forever upskilling every developer. That&apos;s no longer true. You can now use highly complex, high-powered tools simply. You just have to know they exist, and you have to falsify your priors. one source of truthThe demo is up on my GitHub as nix-demo below. Clone it down and have a look, because there are some interesting things in there. I use devenv, which is a nice gentle introduction to Nix. You define your packages and services in Nix, and that one file generates your developer laptops, your CI/CD, your agent sandboxes and your production Docker images.GitHub - ghuntley/nix-demo: Patch git once with a Nix overlay; use it in devenv, a NixOS VM test and a Docker imagePatch git once with a Nix overlay; use it in devenv, a NixOS VM test and a Docker image - ghuntley/nix-demoSee where I&apos;m going? A single source of truth. How many people are spinning up teams right now to figure out agent sandboxes, and are they just duplicating environments? I&apos;d bet that at some of your companies the laptop setup isn&apos;t reproducible: onboard a new employee or lose a laptop, and it&apos;s 48 hours to rebuild the developer environment. Then there&apos;s drift in CI/CD, so it works on your computer but CI says it doesn&apos;t. The agent sandbox is another source of drift. And finally, you say it&apos;s all done, but your software increment doesn&apos;t work in the production Docker image.Interestingly, the Docker images Nix produces are incredibly efficient. Docker basically stacks file-system layers on top of each other and squashes them. Nix is a graph, and it uses that graph to build a very optimised image.Optimising Docker Layers for Better Caching with Nix - Graham Christensena git that cannot force pushImagine I&apos;m a new engineer with a brand new computer, onboarding into the company; all I need to do is change my working directory to the source code checkout. My globally installed git is 2.54, but I cd into the project, and I&apos;m onboarded. Think nvm or a Python version manager, but for all of your operating-system dependencies, including across the FFI boundaries; it goes past the programming language. After changing my working directory git is 2.55. What&apos;s so special about this version of git? It&apos;s not just a newer version.This version of git doesn&apos;t support force push. I&apos;ve monkey-patched it for my agent sandboxes, my local engineering laptops, and everywhere else I use git. It&apos;s a single source of git, so anything that needs git as a transitive dependency also gets my patched version.The best way to stop a model from doing something is to remove its ability to do it.How do you stop an agent from force pushing? It hill-climbs toward its goal and does destructive things along the way. When that causes incidents, remove the capability from the underlying system. I use this trick all over the place, and sometimes the best way is to monkey-patch the system underneath.Those of you from my generation will remember patch files. Open source used to be distributed as a collection of patch files. The idea that everything must be merged upstream on GitHub was never part of open source. This is how we used to do software development. Here I have a closure that defines git, plus my custom patches.How did I get the custom patches? I asked Claude: Can you please use Nix and create a custom overlay that removes force push? Done. Now a set of Unix patches is applied to git automatically whenever I&apos;m in that environment. And it&apos;s not just that environment. It could be Docker, or a production host, wherever you like. This one little pattern makes the entire world patchable. You&apos;re no longer waiting on someone upstream to merge a bug fix. You just route around it.patch the planetThere&apos;s no hidden magic and no skeletons in the closet. I import the overlay and Nix handles the rest. You might think mise is good software. It&apos;s not; it&apos;s a package manager like Homebrew. Does it have this level of functionality? Nix lets you patch anything, including the operating system kernel, and then deploy that custom version across your fleet.About a month before the incidents, I wrote about what happens when there&apos;s a critical fault in OpenSSL. You can update OpenSSL. Cool. But what about when it&apos;s a transitive dependency? OpenSSL is used by Nginx and Postgres, so it isn&apos;t just a matter of patching OpenSSL itself. That&apos;s why we never patched things manually. With a single source of truth for OpenSSL, you apply a monkey patch just like I did with git, and Nix recompiles the world. Every transitive dependency gets the custom version.Nix has good caching and remote builders, similar to Bazel, so this doesn&apos;t mean compiling forever. CI compiles the software once, validates it, and publishes it to the cache, and your developer environments and sandboxes download from it. Simple.So the question I want to put to you is: how much productivity did you lose two weeks ago during those security incidents?I didn&apos;t lose any sleep, folks, because I have a single source of truth. I opened Claude and asked whether my fleet was affected. It said yes, and from there it applied the monkey patches it needed and updated the refs, dependencies, and pins. Because everything flows from that source of truth, the transitive dependencies recompiled automatically. Done. I&apos;m living the nirvana life over here, and you could be too. You just have to know this exists.the AGENTS.md reminder trickThere was one cute trick I did. After the "am I affected?" prompt, I had some temporary monkey patches in place, similar to the git overlay. So I issued another prompt: update the AGENTS.md, and in seven days&apos; time, get rid of my patches.Instead of creating a Jira ticket, I added a reminder to my AGENTS.md. The next developer or agent to pick up that machine automatically did the housekeeping, and backed out the monkey patches and pins because upstream had been fixed. This is the easiest security maintenance I&apos;ve ever done. Every time there&apos;s a security issue, I use these two tricks.If you optimise for this, your security incident response gets faster, and your productivity for factories and everything else gets faster too. The answer for AI is engineering.root, but only in a sandboxI had ten minutes left, so I did a bonus round on loops. Everyone has their own way of doing loop engineering. There are no best practices, and my way is very different from Steve&apos;s. Surprise: mine involves Nix, which has a very powerful testing primitive.everything is a ralph loopI&#x2019;ve been thinking about how I build software is so very very different how I used to do it three years ago. No, I&#x2019;m not talking about acceleration through usage of AI but instead at a more fundamental level of approach, techniques and best practices. Standard software practicesWhen I run my loops, I give my agents sudo. They run as root. Would you do that on an Ubuntu machine? Hell no. But a throwaway Nix developer machine has some unique properties. I can run these loops with sudo, which lets the agent inspect everything from the database to the journals, and it&apos;s safe because I designed the operating environment for it.Here&apos;s why that matters. Nix has a testing framework called the NixOS test. Imagine two web servers with a load balancer in front, on different network VLANs. How would you normally test that? It would be really hard. With Nix, you define what you need; it creates all the machines, and you can assert that your network rules hold.When I run my loops, the entire operating system, the fleet and the higher-tier stack are all under test, integrated from day one. When the agent finishes a unit of work, I test it on exactly what would be production infrastructure, because the infrastructure is defined as code. I can deploy that increment somewhere as a preview environment. Run production from Nix flakes, spin up something identical to production, test the hell out of it, and if it&apos;s green, it will be correct when you apply that flake to production.Having said all that: do not run agents with Nix as root on production hosts, and do not connect agents to production databases. Ever. If you need to reproduce something, build a workflow that duplicates the database and restrict the heck out of outbound network access. Dev parity really is equal at this point. One source of truth, one way up.don&apos;t let the loop closeRalph was never just about loops. It was about stopping the loop from closing on bad code. The loop generates code, commits it, compiles it, and so on. The best way to stop it closing on bad output is deterministic checks. These aren&apos;t skills. This is engineering again.don&#x2019;t waste your back pressureI am fortunate to be surrounded by folks who listen and the link below post will go down as a seminal reading for people interested in AI context engineering. A simple convo between mates - well Moss translated it into words and i&#x2019;ve been waiting for it to come outYou can block a git push if the software doesn&apos;t compile. That&apos;s a pre-commit hook, or prek, and you can engineer a lot of back pressure with hooks. Then add static analysis, such as "this domain must never be coupled to that domain". Say you have an API domain and a SQL domain. You don&apos;t want SQL to reference the API. That would normally be an architecture review, but agents are pretty dumb and will do it anyway. Wondering how to solve your code review problems? Engineer away much of the need for code review with checks like these, using static and semantic analysis from your language&apos;s language service. There&apos;s so much you can do. You just have to ask.property-based testingNext, unit tests. The problem with unit tests is that they only test what you specify, so edge cases slip through. That&apos;s where property-based testing comes in. It has been around for years, and you should be using it.Say you have a function that reverses a string, and the implementation is faulty because it doesn&apos;t support Unicode or emoji. I never wrote that test, so it slips through. That&apos;s a whole category of problems.With property-based testing, a generator feeds in random strings, emoji, huge strings and long strings, and keeps exploring the state space to check that your property holds. The property here is that reversing a string twice gives you back the original string. And I&apos;m not just talking about reversing strings. I&apos;m talking about properties like "a customer who asks for a refund is only refunded once", across the whole lifecycle and all of your microservices. Properties take some getting used to, but they&apos;re really cool.bombadil and hegelAt Antithesis, validation and verification of software is what we do. We have a library called Bombadil. You should ditch Playwright, folks, and I&apos;m not just talking my book. Bombadil lets you write a property, such as "the user always has the ability to log out". It loads your plain JavaScript or TypeScript application in a web browser and puts it through hell: rotating the screen, changing dimensions, going full screen, and committing every random act of violence it can against your app until the property either holds or fails. When it fails, you get a counterexample: a reproduction of exactly how it failed.Fun fact: back in February we woke up to find PewDiePie using it, and we still don&apos;t know how, because this is academic knowledge, not popular knowledge. Maybe it&apos;s in the model weights.We also have Hegel: a small core library written in Rust, with sugar on top for each programming language. You might know its predecessor, Hypothesis. Same team, same tech, but now we&apos;re bringing it to every programming language. Do these two things in your codebase and, beyond solving your patching woes, you&apos;ll get a massive uplift across your organisation. They&apos;re free.
